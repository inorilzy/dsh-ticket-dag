# dsh-ticket-dag

DeepSeek Harness 的本地 Git 工单调度插件。队长交给它一个已确认的 JSON 清单。插件为每张开发工单创建独立分支、worktree 和 DSH 子会话，并行执行就绪工单，将测试通过的候选逐个合入本轮集成分支。运行完成或需要处理时，插件给原队长发送持久消息。

**版本 0.13.0** · DSH `0.2.1-rc.2` 或 `0.2.1-rc.5` · Node.js `^22.19.0 || >=24` · Git **2.43+**。包内含可直接执行的原生 ESM 源码和测试，无须编译。Git 仓库需要已有本地提交、可用的提交身份，以及创建同级 worktree 目录的权限。

## 安装与首次运行

1. 下载 `dsh-ticket-dag-0.13.0.tgz`，保存在运行 DSH 的电脑上。打开侧栏 **插件 → 添加插件 → 安装第三方插件**，输入该文件的本地绝对路径，例如 `D:\DSH-Plugins\dsh-ticket-dag-0.13.0.tgz`，然后安装并启用。使用命令行也可以在目标 profile 安装同一个文件：
   ```powershell
   dsh plugin --profile web add "$HOME\Downloads\dsh-ticket-dag-0.13.0.tgz"
   ```
   旧版用户可以等当前工单结束后，在同一 profile 使用上面的命令升级。SDK profile 将 `web` 换为 `sdk`。安装后重新打开插件详情；若宿主提示需要重启，则重启该 profile。
2. 在 **插件 → 已安装 → dsh-ticket-dag** 中找到同名组件，点 **配置**。先运行示例时，点 **补入示例验收项**，再点 **保存配置**；已设置的同名验收项会保留。没有图形界面的 SDK 环境仍可将 `examples/profile.patch.yml` 中的配置合入当前 profile 的 `cordis.patch.yml`，并保留其他现有配置。
3. 在一个临时 Git 仓库中试跑示例。可以用下面的命令初始化，随后在该仓库启动 DSH。已有项目可直接使用自己的清单。
   ```powershell
   git init -b main dag-playground
   cd dag-playground
   git -c user.name="DAG Demo" -c user.email=demo@example.invalid commit --allow-empty -m "Initial commit"
   ```
   接下来 worker 和集成器也要能提交。请先用 `git config user.name` 和 `git config user.email` 检查仓库是否已有身份；需要时在**此仓库**设置自己的身份。
4. 将 `examples/hello.json` 的内容发给该仓库的队长会话，并附上：
   > 我批准执行这份清单。调用 dag_run，runId 使用 hello-01，manifest 使用上面的 JSON。返回运行 ID 后结束本轮，让插件负责派工，并在完成时通知我。
5. 应先并行执行 A、C，再运行依赖两者的 B。全部通过后检查：
   ```sh
   git log --oneline --first-parent main..integration/hello-01
   git show integration/hello-01:dag-demo/welcome.cjs
   git worktree list
   ```
   `integration/hello-01` 就是交付分支。主工作目录留在原分支，可按自己的流程审查后合到 main 或开 PR。

**宿主配置。** 使用包含 `spawn`、agent、工作目录服务、持久化会话和 Session 查询的 profile，配置可用模型并授权本项目所需的文件与命令操作。测试验收命令在候选 worktree 中执行，依赖须在该环境可用。默认插件上限为 16，清单可设 1–32，实际受宿主 `maxActiveSubagents` 限制。桌面版使用独立的嵌入式宿主，先核对其版本。

## 运行进度

看板跟着对话走：队长对话发起 `dag_run` 后，对话顶部出现 **查看工单** 按钮，点它在右侧栏打开本对话最新一轮运行的标签页。对话里每次 `dag_run` 也会留下一张工单卡片，显示运行 ID、状态、工单数和负责成员，卡片上的 **查看工单** 打开对应那一轮的标签；关掉右侧栏或重新打开会话后，卡片仍在原处。每轮运行有自己的标签，标题为“工单 · 运行 ID”，标签里只显示这一轮；再次打开同一轮会切回已有标签，新的一轮开始时会自动开一个新标签。依赖图排在工单列表前面，标签页内容可上下滚动。已派出的工单在列表和详情卡上有 **查看对话** 按钮，点它打开该工单子会话的对话记录，查看实现过程。打开的标签页每 2 秒读取一次最新状态，对话顶部的“查看工单”入口每 5 秒检查一次是否有新运行；运行结束后放慢到每 30 秒一次。浏览器页面隐藏时暂停读取，重新显示时立即读一次。读取失败时保留上一次的内容并提示“数据可能已过期”，按指数退避重试，最长间隔 30 秒；运行记录返回 404 时停止自动刷新。也可点“刷新进度”。完成数按已合入本轮集成分支的工单计算。子会话刚提交、正在排队试合并或正在验收的工单仍计为进行中。

看板由几块面板组成：显示队长对话当前模型的队长卡；运行概况卡；按“进行中 / 等待 / 需要处理 / 已集成”分段的总进度；可收起、可筛选的工单列表；从左到右按依赖深度排列的工单依赖图。工单行、依赖图节点和详情卡用成员显示名（按成员颜色）标出负责人，而不是预设 ID：优先用预设的显示名，内置预设未存显示名时用内置中文名（实现者 / 测试员 / 文档员），都没有时显示预设 ID，未指定预设的工单显示“默认成员”。节点悬停可看到标题、状态、阶段和模型。点击节点可固定查看该工单的上游、下游、负责成员与模型，以及“工作树 → 启动 → 执行 → 回执 → 试合并 → 验收 → 集成 → 清理”阶段条（最后一步按该工单的清理结果显示已完成或已跳过，悬停可见跳过原因）；它的整条上下游链路会高亮，其余节点变暗。再次点击取消固定。未固定时，详情默认显示最需要关注的工单。

例如 A、C 同时开发、B 依赖两者时，先能看到 B 在等哪些上游；A 先合入，B 仍等 C。C 也合入后，B 才从当前集成提交开工。轮到验收时可查看当前检查 ID 及命令序号；遇到冲突或命令失败，可在工单中查看诊断，再回到原队长会话处理。

运行历史按 profile 保存索引。旧版创建的运行在原队长会话重新接管后出现在看板。宿主重启后，历史记录显示最后持久化的状态；打开看板只读取数据，不会自动恢复派工。

## 图形配置面板

**插件 → Agent 预设** 是专门配置 Agent 的页面：最大 Agent 数量、预设列表，以及每个预设的模型、推理强度和同时运行上限。已保存的预设显示为一行一个的列表，点“编辑”才展开该项，保存或丢弃修改后收起。**插件 → 已安装 → dsh-ticket-dag** 详情页显示同一页面；点该组件的 **配置** 可以编辑下表全部设置，包括验收超时和验收命令。两处读写同一份 profile 配置。

| 设置 | 默认值 | 用途 |
| --- | --- | --- |
| 最大 Agent 数量（并发工单数） | 16（可设 1–32） | 所有运行合计同时派发的工单 Agent 数，单次运行还受清单的 `max_workers` 和宿主容量约束 |
| 验收超时 | 120 秒 | 单条验收命令的时限；在配置文件中以毫秒保存为 `checkTimeoutMs` |
| 验收项 | 空 | 为每个 ID 填入可执行程序和参数，工单用 `verify` 引用。同一个 ID 可以依次执行多条命令 |
| 预设 Agent | `implementer`（实现者）、`test-writer`（测试员）、`docs`（文档员） | 每个预设有显示名、简介、角色说明、模型和推理强度。模型与推理强度从宿主已配置的 provider 模型目录中选择，选“宿主默认”则沿用宿主路由。“同时运行上限”限制用该预设的工单最多同时跑几个，0 表示不单独限制。工单用 `agent` 引用预设 ID |
| `autoCleanup` | 开启 | 运行完成后自动删除已集成工单的 worktree 和分支，见下文“清理”。实时生效 |
| `maxAppendedTickets` | 20 | 单轮运行经 `dag_add` 累计最多追加的工单数，见下文“追加工单”。实时生效 |
| `trackerWriteback` | `off` | 从 GitHub 导入的工单集成后，是否在对应 issue 下评论（`comment`）或评论并关闭（`close`），见“从 spec 和工单导入”。实时生效 |
| `reviewOnComplete` | 关闭 | 配置页“完成后审查一轮”。一轮运行首次全部集成时，“运行完成”通知要求队长用 `code-review` 审查集成分支，并把要修的发现用 `dag_add` 追加为修复工单；修复集成后的完成通知会说明不再重复审查。实时生效 |

预设保存在配置键 `agents` 中。profile 一旦保存了自己的预设，就以保存的这一组为准，内置预设可以修改或删除，“补入内置预设”可以把缺少的内置项加回来。角色说明会写进工单提示词，只约束模型行为，不做文件范围检查；真正的把关仍是验收命令。冻结分两个时点：`dag_run` 时，所用预设的角色说明和模型按当时的配置冻结进这轮运行的清单；开启启动前确认时，用户点 **确认并启动** 的那一刻，插件再按当时的配置重新解析每张工单负责人的预设（取其角色说明），并把用户在审查面板上选定的模型和推理强度一起冻结进各工单的定义。计划中的预设若在这期间已从配置删除，仍沿用 `dag_run` 时冻结的那份。批准后再修改预设，只影响新的运行。同一 `runId` 在预设修改后重新提交，会因清单不同而被拒绝；用原清单重新提交（包括批准之后）则返回已有运行。同时运行上限例外：它和最大 Agent 数量一样实时生效，保存后立即用于后续派工，不中断已在运行的工单；某个预设满额时，只暂缓它的工单，其他就绪工单照常派发。

例如，可以添加一个名为 `git-check` 的验收项，将程序设为 `git`，参数分别设为 `diff`、`--check`、`HEAD^`、`HEAD`。程序和参数由 Git 候选工作树中的进程直接执行。请确认设置中的命令是你愿意在该仓库运行的。

要配足 16 个并发，请同时在 **插件 → 子智能体 → 运行限制** 核对“子智能体并行数量上限”。插件表单只编辑本插件的字段。表单的修改在点击保存时写入当前 DSH profile。调低并发后，在途 worker 可以完成，后续工单等待容量。已打开的运行继续用原验收命令；新运行使用更新后的命令。宿主冷启动恢复旧运行时，若之前使用的命令已被修改，先恢复该组命令再继续。超时修改用于下一批开始的验收。

## 工单与控制工具

清单字段为 `spec_id`、`base_ref`、`max_workers`、`tickets[]`，可选清单级 `checks`。工单至少需要 `id` 和 `title`。建议显式填写 `prompt`、`acceptance`、`depends_on`，可选 `verify`、`produces`、`consumes`、`agent`、`source`（由 `dag_import` 填写的工单来源）和清单级 `external_inputs`。导入时校验重复、未知依赖、环、验收项、预设 Agent 及已声明产物关系。

**验收（可选）。** 每张工单的 `verify` 可以留空或不写：这样的工单在试合并干净、复核候选后直接集成，不跑任何命令，适合文档这类没有命令能检查的工作。写了 `verify` 时，ID 可以来自两处：

- **插件配置里的验收项**：你在配置页登记，不需要额外确认。
- **队长写进清单的 `checks`**：形如 `"checks": {"py-test": [["uv", "run", "pytest", "-q"]]}`，ID 不能与配置里的重名。这些命令要你在右侧栏计划审查的 **验收命令** 区块里看过并批准后才会执行；因此只要清单带了 `checks`，即使关闭了“启动前需要我确认”，这轮运行也会先停在待确认。每个清单最多 20 个 ID，每个 ID 最多 10 条命令，单个参数最长 4096 字符。

验收命令由插件在候选工作树中执行，worker 自己报告的结果不算数。这一层防的是“声称测试通过”和“换成一条什么都不查的命令”，不是权限边界：worker 本身就能执行 shell 命令。

| 工具 | 入参 | 行为 |
| --- | --- | --- |
| `dag_run` | `manifest`、可选 `runId` | 清单可传 JSON 对象或 JSON 字符串。默认 ID 由原队长会话和 spec ID 派生。同一 ID、同一清单重复提交会返回已有运行 |
| `dag_status` | `runId` | 返回各票状态、执行代次、工作目录、分支、基线、成果 SHA、落地 SHA、待投递通知及阻塞原因 |
| `dag_pause` | `runId` | 暂停新工单和新的发布动作；在途 worker 可以提交成果 |
| `dag_resume` | `runId` | 核对发布记录和真实 Git 后继续就绪队列 |
| `dag_retry` | `runId, id`，可选 `isolated` | 对指定阻塞工单核对旧现场，接回完成提交或启动新尝试。无法确认旧 worker 退出时可显式选择 `isolated: true` |
| `dag_cancel` | `runId` | 终止运行、请求停止已知 worker、保留证据，并对已发出的 Git 发布做对账。取消后的 run 为终态 |
| `dag_cleanup` | `runId` | 手动删除该轮已集成工单的 worktree 和分支（包括已结束的运行），返回每张工单的结果。重复调用无害，见下文“清理” |
| `dag_add` | `runId, tickets` | 向已有运行追加工单，`tickets` 为工单数组或其 JSON 字符串。无需再次人工确认，但同样要通过验收，见下文“追加工单” |
| `dag_import` | `spec`，可选 `repo` | 只读：把 GitHub issue 或本地 `.scratch` 中的 spec 和工单转成清单草稿，并给出 `dependencyMode`，见下文“从 spec 和工单导入” |

这 9 个工具限定给原顶层队长。

## 从 spec 和工单导入（`dag_import`）

插件可以直接读取 `/to-spec` 和 `/to-tickets` 发布的 spec 和工单，生成一份 `dag_run` 清单草稿。这一步只读：不启动运行，不写 GitHub，也不改文件。

| 来源 | spec | 工单 | 依赖 |
| --- | --- | --- | --- |
| GitHub | 父 issue（`#1`、`1` 或 issue URL，可用 `repo` 指定 `owner/name`） | 父 issue 的 sub-issues；仓库不支持 sub-issues 时，取正文以 `Part of #1` 开头的 issue | GitHub 原生依赖（blocked-by），以及正文中的 `Blocked by: #n` 行或 `## Blocked by` 段落 |
| 本地 | `.scratch/<slug>/spec.md` | `.scratch/<slug>/issues/NN-*.md` | 文件中的 `Blocked by: 01, 02` 行 |

本地来源可以传 `.scratch/<slug>` 目录、其中的 `spec.md`，或 `issues` 目录。读取 GitHub 需要本机已安装并登录 `gh`。

草稿中每张工单的字段：

- `id`：取标题里的 `[T01]` 标签。标签缺失或重复时，GitHub 工单用 `gh-<编号>`，本地工单用 `T<文件编号>`。
- `title`：去掉标签后的标题。
- `prompt`：工单正文，前面加上工单和 spec 的位置。
- `acceptance`：`Acceptance criteria` 下的复选框。
- `depends_on`：来自上表的依赖。
- `source`：工单来源，跟着工单写进账本。

返回值中的 `dependencyMode` 决定队长接下来怎么做：

- `declared`：跟踪器给出了依赖。队长原样保留工单和 `depends_on`，只补 `verify`、`agent` 和清单 `checks`。觉得某条依赖不对时，向用户报告，不自行修改。
- `none`：有工单，但没有任何依赖声明。队长保留工单，自己推断 `depends_on`，并把每条推断出的依赖的理由写进下游工单的 `prompt`，方便在计划审查里核对。
- `no-tickets`：只有 spec。队长自己拆票并推断依赖，同样写明理由。

依赖的边界情况：

- 已关闭的 issue，以及 `Status` 为 done、resolved、closed 等的本地工单，会被跳过，并列在 `skipped` 中。
- 指向已关闭 issue 的依赖视为已满足。
- 指向 spec 之外、仍未关闭的 issue 的依赖直接报错，插件不猜测。

用户消息里提到 spec、issue 或 `.scratch` 路径时，队长提示词要求先调用 `dag_import`。之后照常走 `dag_run`、右侧栏审查和批准。

**回写 GitHub（`trackerWriteback`，默认关闭）。** 配置项“集成后回写 GitHub 工单”有三档：`off`（不回写）、`comment`（评论）、`close`（评论并关闭）。开启后，一张从 GitHub 导入的工单集成到本轮集成分支时，插件用 `gh issue comment` 在对应 issue 下写明运行 ID、集成分支和落地提交；选 `close` 时再执行 `gh issue close`。

- 每张工单只回写一次。
- 失败时只在账本中记录 `writeback_failed` 事件，不阻塞运行，也不自动重试。
- 本地工单不回写。
- 集成分支此时还没有合入默认分支。选 `close` 前，请确认提前关闭 issue 符合你的流程。

**怎么触发。** 插件就是这个 profile 的 Agent Teams，有两个强制入口：消息以 `/dag` 开头，或消息中任意位置出现 “Agent Teams”（不分大小写，`agent team`、`AgentTeams`、`agent-teams` 也算，可以紧挨中文）。命中时插件在这一步给队长追加一条明确指令，整条消息作为目标；`subagent team`、`agentteamsx` 这类只是包含这几个字母的词不算。其他说法（teams、工单团队、ticket DAG）仍由模型判断：用户明确要求，并且任务能拆成 2 张以上工单时，才由当前对话担任队长调用 `dag_run`；只是提到、讨论或拒绝都不算，单张小改动直接做。提示词同时列出 profile 中已配置的验收项 ID 及其命令（保存配置后即时更新），并告诉队长：验收可选，配置里没有合适的验收项时，可以按仓库实际情况（测试框架、锁文件、CI）在清单里写自己的 `checks`，交给你审批。最稳定的入口是斜杠命令 `/dag <目标>`：消息以 `/dag` 开头时，插件在这一步给队长追加一条明确指令，要求它拆票、调用 `dag_run`，并在待确认时请你到右侧栏审查。`/dagger` 之类或句中提到 `/dag` 不会触发，工单 worker 也收不到这条指令。若同一 profile 还启用了其他 Agent Teams 插件，它们会争用同一说法，建议只保留一个。

**启动前确认（默认开启）。** 配置项 `requireApproval`（配置页“启动前需要我确认”）开启时，`dag_run` 只创建一轮“待确认”的运行，不派出任何工单，对话右侧栏随即显示 **执行前计划审查**：自上而下是步骤条、队长卡、**成员与模型**、**任务与依赖**、**验收命令** 和依赖图，操作按钮固定在底部。**验收命令** 区块逐条列出这轮要跑的命令、来源（队长编写或插件配置）和使用它的工单，并写明哪些工单不跑验收命令。成员就是负责工单的预设，按显示名列出并注明负责哪些工单；模型和推理强度在成员上选择，作用于它负责的全部工单。每名成员的模型只影响它自己。勾选几名成员（或勾选表头的全选）后，表头出现 **修改模型** 和 **推理强度** 下拉，选择后只应用到勾选的成员。任务每项一行，显示负责人和等待的上游；点开一行可以改它的负责人。依赖图的每个节点写明工单 ID、负责人（成员颜色）和任务名，还在等上游的工单用橙色边框标出。默认值取自清单与预设。点 **确认并启动** 后，插件先核对所选模型在宿主模型目录中、推理强度为该模型支持的选项（目录暂不可用时只接受“宿主默认”），再按上文的冻结规则写入各工单并开始派工，队长对话收到“已批准”通知；点 **放弃本次计划**（需再点一次确认）则取消这轮运行。待确认的运行不能由队长用 `dag_resume` 或 `dag_pause` 启动，队长收到的提示会指向右侧栏的「工单 · <runId>」标签；要改工单内容，回到对话让队长重新提交。确认须在发起它的队长对话已打开时进行。关闭该选项后，`dag_run` 立即派工。

**审批接口与账本校验。** 面板通过 owner-only 的 `POST /api/ticket-dag.approve` 提交决定。请求必须是 `Content-Type: application/json`（否则 415），带请求头 `x-dsh-ticket-dag: 1`，且若带 `Origin` 须与本宿主同源（否则 403），用以挡住跨站表单。批准结果只写进各工单的定义，原始清单保持不变，所以 `dag_run` 的幂等比对和验收策略哈希不受批准影响。协调器在内存中记住每轮运行的状态、计划和已批准的工单定义的摘要，在派工、验收和发布前核对 SQLite 账本；发现被外部改动就暂停该轮并通知队长，未经批准的运行退回待确认。局限：这只能发现本进程运行期间的改动；协调器未运行时对账本的修改无法察觉，重新加载时以磁盘上的账本为准，非待确认的运行视为已批准。能写账本文件的本地进程同样能改 Git 和 worktree，这层校验不是权限边界。

**队长与头像。** 队长就是调用 `dag_run` 的那个对话：它拆票、提交清单并接收通知，用的是该对话当前选择的模型。看板顶部的队长卡显示这个模型。队长卡、工单行和依赖图节点上的小人按模型识别厂商：DeepSeek、Claude、Gemini、Grok、GPT、Qwen、Kimi、GLM 各有自己的颜色和缩写，识别不了的显示通用小人。模型为“宿主默认”的工单沿用队长的路由，所以显示队长的小人。小人是插件自绘的简单图形，不是各厂商的商标。

**容易用错的一点。** 每个验收 ID 对应一组 argv 数组，按顺序、无 shell 地执行。示例用 `node -e` 做跨平台断言。Windows 优先使用直接可执行的 `.exe` 或 `node` 加脚本路径；程序名经 `PATH`/`PATHEXT` 解析为 `.cmd` 或 `.bat`（例如 `npm`）时，插件改用 `cmd.exe /d /s /v:off /c` 执行并给每个参数加双引号，参数含 `"`、`%`、`!`、`^`、`&`、`|`、`<`、`>` 或换行时直接拒绝并报错。默认每条命令超时 120000 毫秒，配置键为 `checkTimeoutMs`。不要在验收命令中启动常驻服务器。

## 调度与 Git

- 单次运行绑定 `repo.commonDir + parentId + integration/<runId>`。SQLite 单写者锁防止两个插件进程同时接管同一 run。单一协调器内的所有 run 共用插件并发上限。
- 队长会话打开时自动扫描并接管自己的 run。某一轮被其他协调器持锁、账本损坏或加载失败时，宿主日志按 runId 记录原因，扫描继续处理其他 run，不抢占别人的锁。账本损坏到读不出队长时，扫描该仓库的每个队长都会看到这条诊断。处理后再次打开会话，或对该 run 调用 `dag_status`，会重新尝试接管。
- 每张票启动时先在数据库里领取票、分支、路径和租约，再切换 Git。新票必须从本轮已验证 tip 开始，逐个确认依赖的 `landedSha` 在真实 checkout 的历史中。依赖验证、工作区干净状态与分支检查通过才启动 DSH。
- 实施票在专属的物理 worktree 中运行。**一个结束就补一张 ready 票**，不同层可重叠。子会话和开发目录不会复用给下一张无关工单；在途模型数可以是 16，保留的工单目录数可能大于 16。
- Worker 在最后的提交信息末尾写四条身份 trailer，插件会把准确的值发在任务 prompt 里。提交需要包含本票获准的基线，并保持 worktree 干净。只有与本轮、本票、当前代次匹配的完成提交才进入 `SUBMITTED`。普通 WIP 保留供续做。
- 每次只发布一个候选。在独立 detached worktree 中对当前集成 tip 试合并工单提交，运行该票及所有已集成票声明的验收项（按 ID 去重），复核候选 HEAD 及干净状态。通过后先保存发布意图，再用带预期旧值的 `git update-ref` 推进目标分支，最后记 `INTEGRATED` 并解锁下游。
- 无关票遇到组合冲突或测试失败时，其他可独立完成的票继续。失败票的状态含诊断和工作目录，修复时请针对工单分支提交改进；再次 `dag_retry` 会重新发放执行代次、重建并验证候选。
- 集成 ref 在运行期间由插件独占管理。请勿在外部 checkout 或移动 `integration/<runId>`。遇到陌生 tip 会暂停并通知队长，不会强行覆盖。可用 `git show`、`git log` 或 detached 的只读检出查看内容。

## 清理

**时机。** 一轮运行的全部工单都已集成，且“运行完成”通知已投递给队长后，插件自动清理（`autoCleanup`，默认开启，保存配置后立即生效）。通知尚未送达时不清理；被取消的运行永不清理。关闭 `autoCleanup` 时什么都不删，重新开启后，已完成的运行会补做清理。也可随时让队长调用 `dag_cleanup({ runId })` 手动清理，包括已结束的运行。

**范围。** 只处理状态为已集成的工单，删除它在账本中记录的 worktree 和工单分支，集成分支和其上的提交保持不变。结果按工单落库（已清理 / 已跳过及原因），显示在 `dag_status`、看板的运行概况（“已清理 N 张 / 跳过 M 张”）和阶段条最后一步。已清理的工单不会再处理；被跳过的工单，自动清理不再重试，`dag_cleanup` 会再试一次。重复调用 `dag_cleanup` 无害。

**五层保护。**

1. **只删账本记录**：只用账本里该工单自己的路径和分支，路径必须位于插件的 worktree 根目录之内，主 worktree 一律拒绝。
2. **拒绝集成 / base 分支**：分支名等于本轮集成分支或清单 `base_ref` 指向的本地分支时拒绝；另一 worktree 检出了该分支、或该路径检出的是别的分支时也拒绝。
3. **先确认已合入且无未提交改动**：工单分支不是集成分支的祖先时跳过（“not merged”）；worktree 有未提交改动时跳过（“uncommitted changes”）；路径存在但不是已登记的 worktree 时也跳过。跳过不报错，原因记在该工单上。
4. **不强制删除**：依次执行 `git worktree remove`（不带 `--force`）、以集成分支为上游的 `git branch -d`（不用 `-D`）和 `git worktree prune`。
5. **集成分支永不删除**：`integration/<runId>` 是交付分支，清理只读取它来判断是否已合入。

## 追加工单

运行开始后还要补活时，队长调用 `dag_add({ runId, tickets })`，不要为同一件事再开一轮 `dag_run`。`tickets` 中每张工单遵循与清单相同的规则（`id`、`title`、`prompt`、`depends_on`、`verify`、可选 `agent` 等）；`depends_on` 可以指向本轮已有工单或同一批的工单，仍会校验未知依赖、环和产物关系。只能新增：已有工单不能被修改或删除，ID（不区分大小写）与已有工单重复时拒绝。

- **无需人工审批。** 已批准或无需确认的运行，追加的工单立即进入就绪队列，与其他工单一样经过试合并、验收（如有）和集成。还在待确认的运行则把它们并入右侧栏正在审查的计划，由用户随整份计划一起批准。
- **验收命令。** 本轮已在用的验收 ID 沿用运行冻结的命令；新的验收 ID 按当前配置取命令，并随这批工单一起冻结。追加的工单可以引用清单里队长写的 `checks`，但不能带新的命令，因为追加不经审批。
- **模型沿用规则。** 追加工单的 `agent` 若是本轮已批准过的成员（预设），沿用用户为该成员选定的 provider、模型和推理强度；角色说明按当前配置解析。其他预设按当前配置解析；不写 `agent` 的工单使用默认成员。
- **上限。** 每轮运行经 `dag_add` 累计最多追加 `maxAppendedTickets` 张（默认 20）；超出时报错并提示另开一轮 `dag_run`。
- **幂等与拒绝。** 原样重复提交同一批工单返回已有结果、不重复追加；同一 ID 换了内容再追加会被拒绝。已取消的运行拒绝追加。
- **已完成的运行被重开。** 向全部工单都已集成的运行追加工单后，这轮运行重新变为未完成，新工单照常派发。新工单全部集成后，队长再次收到“运行完成”通知，随后自动清理只处理新工单，此前已清理的工单不受影响。

原清单保持 `dag_run` 提交时的样子，追加的工单另行记录在账本中，并纳入账本防篡改校验。看板和审查面板为追加的工单标出“追加”，悬停可见追加时间；`dag_status` 返回的工单带 `appended` 与 `appendedAt`。

## 中断与持久化

每一轮的数据在 `<git-common-dir>/dsh-ticket-dag/runs/<runId>/state.sqlite`。每票路径由 `dag_status` 返回；默认位于仓库同级的 `.dsh-ticket-worktrees/` 下。数据库、工单分支和工作树应一起保留。运行期间不要移动仓库或手工清除这些目录；运行完成后由插件按上文“清理”的规则删除已集成工单的 worktree 和分支，数据库保留。

| 情况 | 本版处理 |
| --- | --- |
| 模型请求中断 | 优先让 DSH 自身的请求恢复生效。worker 已经明确退出并且错误可识别为暂时性传输故障时，按退避最多自动重试两次。宿主容量不足稍后再派，不扣这个预算 |
| 修改了一半 | 保留原基线、分支、工单目录和未提交修改；确认旧执行者已停止后可对同一票继续。断线时不得把新工单的“必须干净”条件套在旧现场上 |
| 提交了但回执丢失 | 检查原执行代次的完成 trailer，再送入组合验收。缺少完成证据的提交继续作为待处理现场 |
| 无法确认旧会话的写入是否已停止 | 普通重试保持阻塞。确认接受从冻结基线重新开工后，调用 `dag_retry({runId,id,isolated:true})`；新一代使用另一份目录和分支，旧目录/分支保留，旧内容不自动复制 |
| Git 已经前进、SQLite 尚未记账 | 重启对照记录中的旧 tip、确切候选和两个父提交。目标已是候选则补账；仍为旧 tip 且允许继续时重试原发布。陌生状态需要人工核查 |
| 队长不在线 | 通知与状态一起落库，带稳定事件 ID；在原会话恢复时重新投递并去重。宿主支持时使用持久 followup。队长可随时用 `dag_status` 查原有 run |

已退休的插件子会话再次收到消息时，宿主适配器会在模型步骤和工具执行前核对持久租约。工单的旧会话不能继续通过这些入口写文件。这层检查无法终止先前已在系统中运行的外部进程。

插件不会为你回滚 PR、部署或其他外部服务操作。若让 worker 使用有外部副作用的工具，请单独提供幂等键和收据，并在失去回执时先核对外部记录。工作树提供 Git 文件隔离；拥有任意 shell 权限的进程仍可访问其他路径。验收命令超时、取消或输出超限时，插件终止整棵进程树：Windows 上用 `taskkill /T /F`，POSIX 上把命令放进独立进程组再整组结束。主动脱离该进程树或进程组的后台进程仍需要宿主或系统负责终止。

## 开发与测试

源码在 `src/index.mjs`（DSH 入口）、`coordinator.mjs`（调度和恢复）、`git.mjs`（工作树与集成）、`store.mjs`（SQLite 与清单）、`agents.mjs`（内置预设）、`dashboard.mjs`（只读运行快照和历史索引）以及 `client.js`（DSH 原生面板）。测试和示例一同分发。与源文件同目录运行：

```sh
npm test
```

默认测试包含真实临时 Git 仓库、SQLite、并发控制、工单失败恢复及宿主契约测试。要运行真实 DSH 的端到端测试，先安装本版支持的官方 DSH CLI、npm、pnpm 以及 Git，然后设置：

```sh
DSH_TEST_BIN=/absolute/path/to/node_modules/@deepseek-ai/dsh/lib/bin.js \
DSH_TEST_ROLLING=1 node --test test/dsh-e2e.mjs
```

该测试在临时 `DSH_HOME` 中安装打包产物，使用本机回环 SSE 服务模拟模型，实际运行 DSH SDK、子会话、Bash、Git、SQLite 和队长通知。大用例是 18 张票、16 并发、慢任务未结束先补位，最后的依赖票会检查上游文件。测试用的无交互授权仅用于可销毁的本地 fixture。本版尚未验证 Windows 上的端到端流程、桌面安装或真实的商业模型供应商。

真实 Web 面板验收使用 Chromium 和 Puppeteer Core。在上面的 `DSH_TEST_BIN` 之外，设置 `DSH_TEST_CHROME` 为 Chromium 的可执行文件路径，`DSH_TEST_PUPPETEER` 为本机已安装的 puppeteer-core 的 JS 入口，然后运行 `node --test test/web-panel.mjs`。可选 `DSH_TEST_TARBALL` 用于指定实际安装的归档。该测试启动临时 DSH Web，经过真实浏览器验收配置保存、重新打开、启动两张有依赖的工单及看板自动刷新。

## 当前范围

本版面向单机、单仓库和已有 spec/tickets 的 Git 开发任务。只读审核报告暂不作为独立的 DAG 节点；带 `verify` 的工单由可执行验收项把关，不带的只要求干净合并。worker 默认使用宿主模型路由；工单可通过预设 Agent 指定角色说明和模型。已包含：启动前确认（`requireApproval`，默认开启），在右侧栏审查计划，按成员或对勾选的成员批量修改模型与推理强度，按工单改负责人，然后批准或放弃；每轮运行一个右侧栏标签「工单 · <runId>」，对话顶部的“查看工单”打开最新一轮；队长卡与成员显示名；每个预设的同时运行上限；运行完成后自动清理已集成的 worktree 和分支（`autoCleanup`）及手动的 `dag_cleanup`；用 `dag_add` 向已有运行追加工单。审查面板不能修改工单内容、依赖或验收项，这些仍需队长重新提交清单。专门的 LLM reviewer、同目录跨票工位池和自动发布 PR 均未包含。可先用上述 A/C/B 示例确定本机环境，再运行真实开发任务。
